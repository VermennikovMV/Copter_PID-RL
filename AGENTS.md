# Работа с исследовательским snapshot

- Сначала прочитайте README, MODEL_CARD и `v2/docs/joint_applicability_contract_v2.json`.
  Измеренная политика77 и диагностические политики других версий не смешиваются.
- Метрики определяют задачу: каждая обязательная метрика → reward/constraint →
  selector → независимое вычисление. PPO return и имя best_policy не означают PASS.
- Не ослабляйте PID, допуски или правила завершения после просмотра результата.
  Сохраняйте все valid failures. Разделяйте новые и общие полёты; time samples не
  являются независимыми повторениями. Seeds93001/93002/93003 резервны.
- CPU/PyBullet и Gazebo — разные стенды. Software QA, включая baseline-переносимость,
  не подтверждает новые преимущества в Gazebo. Старые ячейки не наследуются новой моделью.
- Для воспроизведения используйте `scripts/reproduce_training.py`: он создаёт
  свежий workspace в `runs/`, выполняет baseline/semantic checks и официальный
  preflight. Внутри workspace действует его собственный корень проекта.
- Файлы `training_capsule/` и `source_archive/` являются версионными исходниками.
  Не отключайте guards и не подменяйте sha(). Для переносимых projections сохраняйте
  отдельно original/export SHA, алгоритмическую и числовую инвариантность.
- Новый checkpoint не заменяет опубликованную модель автоматически. Новые данные
  сначала проверяются по всем обязательным gates, затем явно обновляется версия.
- `MANIFEST.json` и Git blob должны соответствовать байтам. Не включайте EOL
  normalization для hash-bound файлов; `* -text` в .gitattributes намеренно.
- Не добавляйте raw runs, PCAP/BIN, кэши, локальные пути, ключи или токены.
  По запросу владельца публикуются проверенные записи окна Gazebo и терминала
  в `assets/gazebo/`; сохраняйте их происхождение и контрольные суммы.
  Не выдумывайте DOI, GitHub URL, commit, лицензию или невыполненные проверки.
